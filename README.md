# MeshCore-fork — координатор, сенсоры и компаньон на ESP32-S3 + SX1262

Форк прошивки MeshCore для собственной сети из плат Heltec. Одна кодовая база, три роли:

| Роль | Что делает | Окружение | Плата | Чем прошивается |
|---|---|---|---|---|
| **Координатор** | WiFi, MQTT с автообнаружением в Home Assistant, веб-страница OTA, раздача времени, автообновление сети | `heltec_v3_coordinator` | Heltec V3 | `.bin` через страницу OTA или USB |
| **Сенсор** | без WiFi, только LoRa: кнопка, heartbeat, приём прошивки по воздуху | `heltec_v4_3_sensors` | Heltec V4.3 | `.otaz` по воздуху |
| **Компаньон** | всё то же, что сенсор, плюс BLE для телефонного приложения MeshCore | `heltec_v4_3_companion` | Heltec V4.3 | `.otaz` по воздуху |

Все узлы говорят по mesh-протоколу MeshCore и дополнительно — своими сообщениями в
«сенсорном» канале. Имя узла, ключи каналов, WiFi и MQTT в прошивку не вкомпилированы:
они лежат в NVS самого устройства, см. «Настройка устройства». Поэтому один и тот же файл
подходит всем платам своей роли, а образ можно выкладывать открыто.

```
                    WiFi/MQTT                     LoRa 868.731 МГц
   Home Assistant <───────────> Координатор <─────────────────────> Сенсор
                                 (Heltec V3)          │
                                                      └──────────> Компаньон <··BLE··> телефон
                                                                  (Heltec V4.3)
```

## Быстрый старт

```bash
pio run -e heltec_v3_coordinator -e heltec_v4_3_sensors -e heltec_v4_3_companion   # сборка
python3 scripts/selftest.py                       # проверки на ПК, без железа
python3 scripts/provision.py flash Tr1glav_home   # прошить и настроить плату по USB
```

Готовые файлы складываются в `firmware_output/` с версией в имени, по три последних на
плату; для сенсора и компаньона сохраняется только `.otaz`.

## Настройка устройства

Настройки живут в разделе `nvs`, отдельном от разделов прошивки, поэтому переживают любое
обновление — и по USB, и по воздуху. Стирает их только полное стирание флеша
(`esptool erase_flash`), после которого устройство придётся настроить заново.

Ненастроенное устройство не выходит в эфир и пишет об этом при старте; на экране — `NO CONFIG`.

### Скриптом (обычный путь)

Значения лежат в локальном `secrets.json` (он в `.gitignore`, шаблон —
`secrets.example.json`), `scripts/provision.py` прошивает плату по USB и записывает
настройки в её NVS через консоль. Секреты в вывод не попадают: вместо значений печатается
длина.

```bash
python3 scripts/provision.py list                  # какие платы видны (USB-порты)
python3 scripts/provision.py show <имя>            # что будет записано (значения скрыты)
python3 scripts/provision.py flash <имя>           # собрать, прошить, настроить и сверить
python3 scripts/provision.py config <имя>          # только настроить, без прошивки
python3 scripts/provision.py verify <имя>          # сверить настройки на плате с файлом
```

Устройство выбирается по **имени узла** — это ключ в разделе `devices`, он же уезжает в
настройки платы. Раздел `common` задаёт общие значения, поля внутри устройства их
перекрывают. Набор полей зависит от роли:

| Роль | Поля |
|---|---|
| `bot` (координатор) | имя, WiFi, MQTT, приватный и сенсорный каналы, канал команд, радио |
| `sensor` | имя, сенсорный канал, радио |
| `companion` | имя, приватный и сенсорный каналы, радио |

Компаньону приватный канал нужен именно потому, что в приложении это обычный чат: без
ключа он в списке каналов не появится.

Записываются только поля, отличающиеся от текущих настроек платы: скрипт сначала читает
их и сравнивает. Если всё совпадает, не пишется ничего и перезагрузки не происходит. Ключ
`--force` записывает весь набор.

Консоль у плат на разных портах: у Heltec V3 разъём заведён на мост CP2102
(`/dev/ttyUSB*`), у V4.3 — нативный USB чипа (`/dev/ttyACM*`).

### Руками (если скрипта под рукой нет)

Через USB-консоль на 115200 (`pio device monitor`).

```
help                      список команд
show                      показать настройки (пароли скрыты)
show all                  показать вместе с паролями и ключами
set name Tr1glav_sensor   имя узла: адресат mesh OTA и устройство в Home Assistant
set sns_name #sensors     канал сенсоров (нужен всем ролям)
set sns_key <base64>      ключ канала: base64 от 16 байт; пусто — автоключ по имени
set prv_name / prv_key    приватный канал (координатор и компаньон)
set wifi_ssid / wifi_pass только координатор
set mqtt_host <адрес>     только координатор; ещё mqtt_port, mqtt_user, mqtt_pass
set tx_ch #connections    канал, в который уходят команды из Home Assistant
set lora_freq 868.731018  параметры радио: ещё lora_bw, lora_sf, lora_cr, lora_tx,
                          lora_pre, lora_sync — обязаны совпадать у всех узлов сети
set tz 3                  часовой пояс, часы от UTC
set disp_bri 255          яркость экрана 0..255
set vext_on 0             уровень, включающий питание периферии (см. ниже)
set auto_upd 1            ставить новые версии из релизов GitHub
bri <0..255>              применить яркость сразу, без save и перезагрузки
vext <0|1>                переключить питание периферии сразу
save                      записать в NVS
reboot                    перезагрузить (настройки применяются при старте)
```

Имя узла обязано быть уникальным: одноимённые сообщения координатор отбрасывает, а mesh
OTA адресует узел именно по имени.

### Версия

`version.txt` хранит версию, хэш исходников и время сборки. `scripts/gen_version.py` перед
сборкой считает хэш `src/`, `lib/`, `boards/`, `variants/` и `platformio.ini`: изменился
код — номер сборки растёт, нет — остаётся прежним. Значения попадают в код через
сгенерированный `lib/meshcore/include/build_info.h` (в git не хранится), а не через флаги
компилятора: иначе менялась бы команда компиляции всех файлов и пересобиралось бы ядро со
всеми библиотеками.

## Компаньон: телефонное приложение по BLE

Компаньон — это сенсорный узел, к которому по Bluetooth подключается официальное
приложение MeshCore. Протокол повторён по оригиналу побайтово: сервис Nordic UART
(`6E400001-…`), кадр `[код][данные]`, числа little-endian, до 176 байт в кадре.

**Сопряжение.** Приложение подключается только к сопряжённому устройству: обе
характеристики доступны исключительно по зашифрованной связи с подтверждением личности
(`ESP_GATT_PERM_*_ENC_MITM`, режим `SC_MITM_BOND`). Код сопряжения — шестизначный,
случайный при каждом запуске — показывается **во весь экран** и держится там, пока
сопряжение не состоится. Подсмотреть его можно только у самого устройства.

Размер пакета задаётся явно (`setMTU(176)`): иначе ATT MTU остаётся 23 байта, в
уведомление влезает 20, и приложение получает обрезанный ответ на первую же команду —
со стороны это выглядит как «подключается и висит».

**Что умеет**

| Команда | Что делает |
|---|---|
| 1 `APP_START`, 22 `DEVICE_QUERY` | представиться: ключ, радио, версия прошивки, вместимость |
| 5 / 6 `GET/SET_DEVICE_TIME` | часы устройства |
| 4 `GET_CONTACTS`, 9 `ADD_UPDATE_CONTACT`, 15 `REMOVE_CONTACT`, 30 `GET_CONTACT_BY_KEY` | список узлов |
| 13 `RESET_PATH`, 42 `GET_ADVERT_PATH` | маршрут до узла: забыть и показать |
| 31 `GET_CHANNEL`, 32 `SET_CHANNEL` | каналы: перечисление и вступление |
| 2 `SEND_TXT_MSG`, 3 `SEND_CHANNEL_TXT_MSG` | личное сообщение и сообщение в канал |
| 10 `SYNC_NEXT_MESSAGE` | забрать входящее из очереди |
| 7 `SEND_SELF_ADVERT`, 8 `SET_ADVERT_NAME` | объявить себя, переименоваться |
| 20 `GET_BATT_AND_STORAGE` | заряд |
| 54, 64 (области рассылки) | областей у нас нет, отвечаем «не задана» |

Остальные команды получают честный отказ `ERR_CODE_UNSUPPORTED_CMD`, а не молчание.

**Контакты** строятся из адвертов: услышали узел — запомнили ключ, имя, тип, координаты и
маршрут, которым пришёл адверт. Список хранится в NVS (до 16 узлов) и переживает
перезагрузку. Новый узел уходит в приложение полным кадром, знакомый — коротким.

**Ограничения, о которых стоит знать.** Подтверждений доставки прошивка не отслеживает,
поэтому метка в ответе на личное сообщение нулевая: приложение не будет вечно ждать
подтверждения, которого не будет. Текст личного сообщения ограничен 200 байтами
(`DM_TEXT_MAX`), входящее сообщение канала — 165 байтами: столько несёт кадр BLE.
Каналы, заданные настройками устройства, приложению на запись не отдаются — сохранить
такую правку негде, и после перезагрузки она молча откатилась бы.

Сообщения, которые устройство отправило само (кнопка, `hello`), попадают в переписку, но
без сигнала «есть новое»: уведомление о собственном действии телефону ни к чему.

## Сообщения в сенсорном канале

| Сообщение | Кто шлёт | Смысл |
|---|---|---|
| `hello:<версия>:<заряд %>:<напряжение>:<код платы>:<окружение>` | сенсор, компаньон | heartbeat раз в 10 минут, при старте и по запросу; `-` вместо значения, если заряд не измеряется |
| `hello?` | координатор | просьба отметиться; узлы отвечают со случайной задержкой до 4 с |
| `button` / `button2` | сенсор | одиночное и двойное нажатие |
| `ping:<номер>` | сенсор | проверка связи по тройному нажатию кнопки |
| `pong:<номер>:<rssi>:<snr>` | координатор | ответ с его уровнем приёма — видно связь в обе стороны |
| `time:<epoch>:<версия координатора>` | координатор | синхронизация часов раз в 5 минут; расхождение версий узел показывает звёздочкой у версии на экране |
| `ota:…` | обе стороны | управление прошивкой по радио |
| `cfg:<имя>:<поле>=<значение>` | координатор | настройка узла по радио; также `:save`, `:reboot`, `:get` |
| `cfg:ok:<что>` / `cfg:err:<что>` / `cfg:val:…` | узел | подтверждение, отказ или текущие несекретные настройки |

Поле **окружения** в `hello` — не украшение: сенсор и компаньон стоят на одной плате с
одинаковым кодом `h43`, и без него автообновление залило бы компаньону образ сенсора,
после чего BLE с него просто исчез бы. Узлы со старой прошивкой окружения не передают —
для них файл по-прежнему подбирается по коду платы.

Всё, что приходит от узлов, координатор публикует в MQTT: `<префикс>/sensor/<имя>/` +
`text`, `rssi`, `version`, `battery`, `voltage`, `board`, `available`, `button`. В поле
`board` уходит полное имя окружения, а карточка устройства в Home Assistant называется по
роли — `MeshBot Companion <имя>`, `MeshBot Sensor <имя>`.

## Проверка связи с кнопки

Три нажатия подряд на кнопке узла отправляют координатору эхо-запрос, и на экран выводится
результат: время обмена, качество приёма в обе стороны и число ретрансляций.

```
LINK TEST
rtt:  412 ms
rx:   -52 dBm
snr:  9.0 dB
peer: -48 dBm
hops: 0 (direct)
```

Экран устройства везде на английском — при 21 символе в строке это надёжнее, чем кириллица
через перекодировку.

Запрос уходит **одиночной** посылкой, а не повторами, как остальные сообщения: иначе во
время ответа мерялись бы повторы, и число теряло бы смысл. Строка «peer» берётся из ответа
координатора — это его собственный уровень приёма, поэтому асимметрия канала (слышу
хорошо, а меня плохо) видна сразу. Результат держится на экране 15 секунд.

Нажатия различаются по паузе между ними: одно — `button`, два — `button2`, три — проверка
связи; окно следующего нажатия задаётся `SNS_BTN_DBL_WINDOW_MS` (700 мс). Счёт ведётся
без остановки главного цикла: ожидание в циклах с `delay()` задерживало бы приём радио и
обслуживание BLE почти на полторы секунды.

## Эфир: повторы и длина пути

Сообщение уходит в эфир **дважды** с паузой 60 мс (`FLOOD_RETRY_MS`): приёмник отбрасывает
дубликат по хэшу, а вторая копия спасает от коллизии. Третья копия только занимала эфир и
задерживала следующую передачу.

Старшие два бита байта длины пути задают размер хэша одного ретранслятора, младшие шесть —
число хопов. Вся сеть обязана считать одинаково, поэтому значение одно на все платы:
**два байта на хоп** (`PATH_HASH_SIZE`), то есть меньше совпадений хэшей, а при пути в
64 байта — максимум 32 ретрансляции.

## Автообновление из релизов GitHub

Координатор раз в 6 часов спрашивает у GitHub последний релиз и сверяет версии. Файл
выбирается **по имени окружения узла**: `<окружение>_v<версия>.otaz` для узлов и
`<окружение>_v<версия>.bin` для себя. Сначала обновляются узлы — по одному за проход,
потому что прошивка по радио занимает эфир целиком, — и лишь потом координатор сам себя:
собственное обновление означает перезагрузку и потерю сессии. После удачной сессии
следующая проверка не ждёт полный цикл, а идёт через 10 минут.

Прошивка не содержит секретов, поэтому файлы релиза лежат открыто и качаются без токена.
Сертификаты не проверяются (`setInsecure`): корневые пришлось бы носить в прошивке и
обновлять при их смене. Защита здесь другая — маркер платы в образе и CRC32, которые
проверяются до записи.

Выключается настройкой `auto_upd`.

## Прошивка узла по радио (mesh OTA)

1. Координатор получает `.otaz` и сохраняет в LittleFS как `/ota.bin`.
2. `ota:start:<имя>:<размер образа>:<crc32>:z<размер сжатого потока>` — в сенсорном канале.
3. Узел отвечает `ota:ackstart:1`, обе стороны переходят на быстрый канал (GFSK
   250 кбит/с, девиация 125 кГц, полоса приёмника 467 кГц, 868.95 МГц) и дальше общаются
   сырыми кадрами вне meshcore. Параметры канала связаны: полоса обязана покрывать
   `2*(девиация + скорость/2)`, а индекс модуляции `2*девиация/скорость` держат около
   единицы — попытка поднять только скорость, оставив прежние девиацию и полосу, связь
   разваливает.
4. Координатор шлёт пачками по 16 кадров: `[BE EF][тип][seq 4B][MAC 2B][шифр][crc16 2B]`,
   чанк 240 Б, шифрование ключом канала. Последний кадр пачки просит подтверждение.
5. Узел отвечает `WACK`: номер первого недостающего чанка и битовая маска следующих.
   Потерянные кадры уходят заново, целую пачку переспрашивает кадр `POLL`.
6. `DONE` → узел сверяет CRC32 всего образа, пишет его и перезагружается, ответив `DONE_ACK`.

Узел распаковывает поток на лету (`tinfl` из ROM ESP32-S3), поэтому по радио идёт сжатый
образ — примерно 60% исходного размера.

Замеры на стенде (образ 270 КБ, платы в одной комнате): исходно 74 с и 3.71 КБ/с; окно
подтверждений 16 вместо 8, отказ от возврата в приём между кадрами пачки и пауза 8 мс
вместо 15 дали 54 с и 4.87 КБ/с; переход на 250 кбит/с — **38 с и 6.93 КБ/с**, вдвое
быстрее исходного. Паузу 4 мс пробовали и отвергли: узел перестаёт успевать, растут
повторы и опросы, и сессия становится длиннее.

### Формат `.otaz`

`[OTAZ][размер образа 4B LE][CRC32 образа 4B LE][zlib-поток]` — собирает
`scripts/copy_firmware.py` после сборки.

### Маркер платы

Каждая прошивка несёт строку `MBFW:<код платы>:<версия>`. Координатор сканирует
загружаемый `.bin`, узел — распакованный образ, и прошивка от другой платы отклоняется до
записи: она не запустится, а снимать её пришлось бы USB-кабелем. Образ без маркера (сборка
старше этой проверки) принимается, о чём остаётся запись в логе.

## Веб-страница координатора (порт 3232)

| Адрес | Назначение |
|---|---|
| `/` | страница: цели, загрузка файла, прогресс, живые логи |
| `/style.css`, `/app.js` | статика из `web/`, отдаётся сжатой (`Content-Encoding: gzip`) |
| `/info` | состояние: uptime, WiFi/MQTT, IP, температура, память, заряд, окружение, файл |
| `/sensors` | список узлов: версия, окружение, заряд, RSSI, когда выходил на связь |
| `/sensors/hello` | разослать `hello?` |
| `/update` | самопрошивка координатора `.bin` |
| `/savefw` | загрузка `.otaz` |
| `/ota/start`, `/ota/abort`, `/ota/status` | управление сессией и её состояние |
| `/logs`, `/logs/tail?from=N` | диагностика и новые строки лога |
| `/config` | настройки координатора: `GET` — список полей (секреты маской), `POST` — изменить |
| `/sensors/config` | настройки узла по радио: `target` и изменяемые поля, плюс `save`/`reboot` |
| `/selftest` | проверка записи в LittleFS |

Страница открыта без пароля: любой в сети может прошить координатор или узел.

Разметка лежит в коде (`ota.cpp`), а стили и сценарий — обычными файлами в `web/`: их
удобно править и проверять инструментами. Перед сборкой `scripts/gen_web.py` сжимает их в
`lib/meshcore/include/web_assets.h`. В цифрах: 16.1 КБ сценария превращаются в 5.7 КБ,
4.4 КБ стилей — в 1.4 КБ, прошивка похудела на 18.5 КБ, страница грузится вчетверо быстрее.

## Настройка узлов по радио

Со страницы координатора можно менять настройки узла, не подключая его по USB: поля уходят
по одному в сенсорный канал, узел подтверждает каждое сообщением `cfg:ok:<поле>`, и ответы
видны в журнале на странице.

Команды уходят с паузой в две секунды. Это не запас на всякий случай: радио полудуплексное,
а подтверждение узла занимает эфир около секунды — посланная раньше следующая команда
просто не будет услышана. На коротком интервале терялся именно `save`.

Присваивание идёт **только в память узла**. В NVS настройки попадают лишь по команде
`save`, поэтому неудачная правка чинится снятием питания. Если правки были, а
подтверждающий `save` не пришёл за две минуты (`CFG_PENDING_REVERT_MS`), узел
перезагружается сам и возвращается к сохранённым настройкам.

Опасные поля остаются опасными: смена имени, ключа или имени канала и параметров радио
после сохранения и перезагрузки уводит узел из сети, и вернуть его можно будет только по
USB. Страница предупреждает об этом перед отправкой.

## Питание периферии и яркость экрана

На Heltec V3 питание периферии (`Vext`, GPIO36) включается **низким** уровнем, на V4.3 —
тоже низким. Это проверено на плате: при высоком уровне экран продолжает работать, но
питается паразитно — заметно тусклее и странно отзывается на запись регистров. Значение
задаётся настройкой `vext_on` (1 = HIGH, 0 = LOW).

Яркость (`disp_bri`, 0..255) применяется один раз в конце инициализации. Раскладка на
регистры контраста, предзаряда и VCOMH сделана так же, как в библиотеке, которую используют
Meshtastic и MeshCore, и завершается командами включения экрана: запись контраста без них
гасила панель.

Аккумулятор: если напряжение около нуля (батарея не подключена), индикатор на экране не
рисуется, а в `hello` вместо заряда и напряжения уходят прочерки.

## Ветки, сборка и выпуск

`develop` — основная ветка репозитория: на неё попадает свежий клон, и в неё уезжает код
после каждой успешной сборки. Ветки `main` в проекте нет.

```bash
pio run                                 собрать, закоммитить и отправить develop
RELEASE=1 pio run                       плюс ветка release/v<версия> — она запускает выкладку
NOGIT=1 pio run                         собрать, ничего не трогая в git
python3 scripts/release.py --dry-run    посмотреть, что попадёт в коммит
```

Коммит делается только после успешной сборки: фиксировать код, который не компилируется,
смысла нет. Сетевые ошибки сборку не роняют — скрипт сообщит, что отправить не удалось, и
оставит коммит на месте.

### Выкладка файлов прошивки

Файлы прошивки в репозиторий не кладутся (`firmware_output/` в `.gitignore`). Их собирает
и публикует GitHub Actions — `.github/workflows/build.yml`:

1. на каждый push прогоняются проверки `scripts/selftest.py` и сборка **всех трёх** окружений;
2. собранные `.bin` и `.otaz` сохраняются как артефакт запуска;
3. если ветка называется `release/v*`, создаётся релиз с тегом `v<версия>`, и файлы
   прикладываются к нему.

Шаги идут последовательно в одном задании, поэтому релиз физически не может появиться,
если упали тесты или сборка. Каждое окружение, которое стоит на реальной плате, обязано
собираться в этом workflow: иначе релиз выйдет без образа для этой платы, а автообновление
не найдёт файл по имени окружения.

Перед коммитом список файлов дополнительно проверяется на `secrets.ini`, `secrets.json`,
`firmware_output/` и `build_info.h`. Их исключает и `.gitignore`, но цена ошибки здесь —
пароли и ключи каналов в истории публичного репозитория, поэтому проверка продублирована.
