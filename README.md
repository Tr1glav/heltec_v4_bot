# MeshCore bot + сенсоры (ESP32-S3, SX1262)

Две роли одной прошивки:

* **бот** (`MQTT_ENABLED`) — WiFi, MQTT с автообнаружением в Home Assistant, веб-страница OTA;
* **сенсор** (`SENSOR_NODE`) — без WiFi, только LoRa: кнопка, heartbeat, приём прошивки по воздуху.

Обе роли говорят по mesh-протоколу MeshCore и дополнительно по своим сообщениям в «сенсорном»
канале. Имя узла, ключи каналов, WiFi и MQTT в прошивку не вкомпилированы — они хранятся
в NVS самого устройства, см. «Настройка устройства».

## Сборка и прошивка

| Плата | Окружение | Код платы | Чем прошивать |
|---|---|---|---|
| Heltec V3 (бот) | `heltec_v3_coordinator` | `h3` | `.bin` через страницу OTA |
| Heltec V4.3 (сенсор) | `heltec_v4_3_sensors` | `h43` | `.otaz` по воздуху |

```bash
pio run -e heltec_v3_coordinator -e heltec_v4_3_sensors   # сборка
pio run -e heltec_v4_3_sensors -t upload           # прошивка по USB
python3 scripts/selftest.py                        # проверки на ПК, без железа
```

Готовые файлы складываются в `firmware_output/` с версией в имени, по 3 последние на плату.
Для сенсоров сохраняется только `.otaz`.

Образ не содержит ни паролей, ни ключей, ни имени узла, поэтому один и тот же файл подходит
всем платам своего типа: два сенсора обновляются одним `.otaz`.

## Настройка устройства

Настройки живут в разделе `nvs`, который лежит отдельно от разделов прошивки, поэтому
переживают любое обновление — и по USB, и по воздуху. Стирает их только полное стирание
флеша (`esptool erase_flash`), после которого устройство придётся настроить заново.

Ненастроенное устройство не выходит в эфир и пишет об этом при старте, на экране — `NO CONFIG`.

### Скриптом (обычный путь)

Значения лежат в локальном `secrets.json` (он в `.gitignore`, шаблон — `secrets.example.json`),
`scripts/provision.py` прошивает плату по USB и записывает настройки в её NVS через консоль.
Секреты в вывод скрипта не попадают: вместо значений печатается длина.

```bash
python3 scripts/provision.py import-ini            # разово: перенести secrets.ini в secrets.json
python3 scripts/provision.py list                  # какие платы видны (USB-порты)
python3 scripts/provision.py show <имя>            # что будет записано (значения скрыты)
python3 scripts/provision.py flash <имя>           # собрать, прошить, настроить и сверить
python3 scripts/provision.py config <имя>          # только настроить, без прошивки
python3 scripts/provision.py verify <имя>          # сверить настройки на плате с файлом
```

Устройство выбирается по **имени узла** — это ключ в разделе `devices`, он же уезжает
в настройки платы. Раздел `common` задаёт общие значения, поля внутри устройства их
перекрывают; роль `bot` получает весь набор, роль `sensor` — имя, канал сенсоров и радио.
Поля, которых в `secrets.json` нет, на плате не трогаются. Порт берётся из поля `port`,
иначе `--port`, иначе определяется автоматически, если USB-плата одна.

Консоль у плат на разных портах: у Heltec V3 разъём заведён на мост CP2102
(`/dev/ttyUSB*`), у V4.3 — нативный USB чипа (`/dev/ttyACM*`).

Записываются только те поля, которые отличаются от текущих настроек платы: скрипт
сначала читает их и сравнивает. Если всё совпадает, не пишется ничего и перезагрузки не
происходит. Ключ `--force` записывает весь набор.

Сверка после записи не раскрывает секреты в выводе скрипта: печатаются только длины.

### Руками (если скрипта под рукой нет)

Через USB-консоль на 115200 (`pio device monitor`).

```
help                      список команд
show                      показать настройки (пароли скрыты)
show all                  показать вместе с паролями и ключами
set name Tr1glav_sensor   имя узла: адресат mesh OTA и устройство в Home Assistant
set sns_name #sensors     канал сенсоров (нужен обеим ролям)
set sns_key <base64>      ключ канала: base64 от 16 байт; пусто — автоключ по имени
set wifi_ssid <сеть>      только бот
set wifi_pass <пароль>    только бот
set mqtt_host <адрес>     только бот; ещё mqtt_port, mqtt_user, mqtt_pass
set prv_name / prv_key    приватный канал бота
set tx_ch #connections    канал, в который уходят команды из Home Assistant
set lora_freq 868.731018  параметры радио: ещё lora_bw, lora_sf, lora_cr,
                          lora_tx, lora_pre, lora_sync — обязаны совпадать
                          у всех узлов сети
set tz 3                  часовой пояс, часы от UTC
set disp_bri 255          яркость экрана 0..255
set vext_on 0             уровень, включающий питание периферии (см. ниже)
bri <0..255>              применить яркость сразу, без save и перезагрузки
vext <0|1>                переключить питание периферии сразу
save                      записать в NVS
reboot                    перезагрузить (настройки применяются при старте)
```

Имя узла обязано быть уникальным: одноимённые сообщения бот отбрасывает, а mesh OTA
адресует сенсор именно по имени. Значение пароля не должно начинаться или заканчиваться
пробелом — консоль обрезает их у введённой строки.

### Версия

`version.txt` хранит версию, хэш исходников и время сборки. `scripts/gen_version.py` перед
сборкой считает хэш `src/`, `lib/`, `boards/`, `variants/` и `platformio.ini`: изменился код —
номер сборки растёт, нет — остаётся прежним. Значения попадают в код через сгенерированный
`lib/meshcore/include/build_info.h` (в git не хранится), а не через флаги компилятора: иначе
менялась бы команда компиляции всех файлов и пересобиралось бы ядро со всеми библиотеками.

## Сообщения в сенсорном канале

| Сообщение | Кто шлёт | Смысл |
|---|---|---|
| `hello:<версия>:<заряд %>:<напряжение>:<код платы>` | сенсор | heartbeat раз в 10 минут, при старте и по запросу; `-` вместо значения, если заряд не измеряется |
| `hello?` | бот | просьба отметиться; сенсоры отвечают со случайной задержкой до 4 с |
| `button` / `button2` | сенсор | одиночное и двойное нажатие |
| `time:<epoch>:<версия бота>` | бот | синхронизация часов раз в 5 минут; расхождение версий сенсор показывает звёздочкой у версии на экране |
| `ota:fail:<причина>` | сенсор | отказ до перехода на быстрый канал — бот покажет причину на странице вместо голого таймаута |
| `cfg:<имя>:<поле>=<значение>` | бот | настройка сенсора по радио; также `cfg:<имя>:save`, `:reboot`, `:get` |
| `cfg:ok:<что>` / `cfg:err:<что>` / `cfg:val:…` | сенсор | подтверждение, отказ или текущие несекретные настройки |

Всё, что приходит от сенсоров, бот публикует в MQTT: `<префикс>/sensor/<имя>/` + `text`,
`rssi`, `version`, `battery`, `voltage`, `board`, `available`, `button`.

## Прошивка сенсора по радио (mesh OTA)

1. Бот получает `.otaz` (см. ниже) и сохраняет в LittleFS как `/ota.bin`.
2. `ota:start:<имя>:<размер образа>:<crc32>:z<размер сжатого потока>` — в сенсорном канале.
3. Сенсор отвечает `ota:ackstart:1`, обе стороны переходят на быстрый канал (GFSK
   250 кбит/с, девиация 125 кГц, полоса приёмника 467 кГц, 868.95 МГц) и дальше общаются
   сырыми кадрами вне meshcore. Параметры канала связаны: полоса обязана покрывать
   `2*(девиация + скорость/2)`, а индекс модуляции `2*девиация/скорость` держат около
   единицы — попытка поднять только скорость, оставив прежние девиацию и полосу, связь
   разваливает.
4. Бот шлёт пачками по 8 кадров: `[BE EF][тип][seq 4B][MAC 2B][шифр][crc16 2B]`, чанк 240 Б,
   шифрование ключом канала. Последний кадр пачки просит подтверждение.
5. Сенсор отвечает `WACK`: номер первого недостающего чанка и битовая маска следующих.
   Потерянные кадры бот шлёт заново, целую пачку переспрашивает кадром `POLL`.
6. `DONE` → сенсор сверяет CRC32 всего образа, пишет его и перезагружается, ответив `DONE_ACK`.

Сенсор распаковывает поток на лету (`tinfl` из ROM ESP32-S3), поэтому по радио идёт сжатый
образ — примерно 60% исходного размера.

Замеры на стенде (образ 270 КБ, платы в одной комнате): исходно 74 с и 3.71 КБ/с; окно
подтверждений 16 вместо 8, отказ от возврата в приём между кадрами пачки и пауза 8 мс
вместо 15 дали 54 с и 4.87 КБ/с; переход на 250 кбит/с — **38 с и 6.93 КБ/с**, то есть
вдвое быстрее исходного. Паузу 4 мс пробовали и отвергли: сенсор перестаёт успевать,
растут повторы и опросы, и сессия становится длиннее. Раскладка времени на 250 кбит/с:
передача 19 с, паузы 9 с, ожидание квитанций ~9 с, чтение с файловой системы и
шифрование — 1.1 с, то есть 3%.

### Формат `.otaz`

`[OTAZ][размер образа 4B LE][CRC32 образа 4B LE][zlib-поток]` — собирает
`scripts/copy_firmware.py` после сборки сенсорного окружения.

### Маркер платы

Каждая прошивка несёт строку `MBFW:<код платы>:<версия>` (`FW_MARKER` в `config.h`,
сама строка определена в `globals.cpp`). Бот сканирует загружаемый `.bin`, сенсор —
распакованный образ, и прошивка от другой платы отклоняется до записи: она не
запустится, а снимать её пришлось бы USB-кабелем. Образ без маркера (сборка старше
этой проверки) принимается, о чём остаётся запись в логе.

## Веб-страница бота (порт 3232)

| Адрес | Назначение |
|---|---|
| `/` | страница: цели, загрузка файла, прогресс, живые логи |
| `/style.css`, `/app.js` | статика из `web/`, отдаётся сжатой (`Content-Encoding: gzip`), кэшируется браузером |
| `/info` | состояние бота: uptime, WiFi/MQTT, IP, температура, память, заряд, файл на боте |
| `/sensors` | список сенсоров: версия, плата, заряд, RSSI, когда выходил на связь |
| `/sensors/hello` | разослать `hello?` |
| `/update` | самопрошивка бота `.bin` |
| `/savefw` | загрузка `.otaz` на бот |
| `/ota/start`, `/ota/abort`, `/ota/status` | управление сессией и её состояние |
| `/logs`, `/logs/tail?from=N` | диагностика и новые строки лога |
| `/config` | настройки бота: `GET` — список полей (секреты маской), `POST` — изменить |
| `/sensors/config` | настройки сенсора по радио: `target` и изменяемые поля, плюс `save`/`reboot` |
| `/selftest` | проверка записи в LittleFS |

Страница открыта без пароля: любой в сети может прошить бота или сенсор.

## Настройка сенсоров по радио

Со страницы бота можно менять настройки сенсора, не подключая его по USB: поля уходят по
одному в сенсорный канал, сенсор подтверждает каждое сообщением `cfg:ok:<поле>`, и ответы
видны в журнале на странице.

Команды уходят с паузой в две секунды. Это не запас на всякий случай: радио
полудуплексное, а подтверждение сенсора шлётся тройным флудом и занимает эфир около
полутора секунд — посланная раньше следующая команда просто не будет услышана. На
коротком интервале терялся именно `save`.

Кнопка «Запросить текущие» шлёт `cfg:<имя>:get`, и сенсор отвечает своими настройками —
несколькими сообщениями, если всё не помещается в одно (лимит группового сообщения около
200 символов). Пароли и ключи в ответ не попадают, пустые поля пропускаются.

Присваивание идёт **только в память сенсора**. В NVS настройки попадают лишь по команде
`save`, поэтому неудачная правка чинится снятием питания. Если правки были, а
подтверждающий `save` не пришёл за две минуты (`CFG_PENDING_REVERT_MS`), сенсор
перезагружается сам и возвращается к сохранённым настройкам — на случай, если связь
оборвалась на середине.

Опасные поля остаются опасными: смена имени, ключа или имени канала и параметров радио
после сохранения и перезагрузки уводит сенсор из сети, и вернуть его можно будет только
по USB. Страница предупреждает об этом перед отправкой.

## Питание периферии и яркость экрана

На Heltec V3 питание периферии (`Vext`, GPIO36) включается **низким** уровнем, на V4.3 —
тоже низким. Это проверено на плате: при высоком уровне экран продолжает работать, но
питается паразитно — заметно тусклее и странно отзывается на запись регистров. Значение
задаётся настройкой `vext_on` (1 = HIGH, 0 = LOW), значение по умолчанию приходит из
`platformio.ini` для каждой платы.

Яркость (`disp_bri`, 0..255) применяется один раз в конце инициализации. Раскладка на
регистры контраста, предзаряда и VCOMH сделана так же, как в библиотеке, которую
используют Meshtastic и MeshCore, и завершается командами включения экрана: запись
контраста без них гасила панель. Применять яркость сразу после `display.begin()` нельзя
по той же причине.

Аккумулятор: если напряжение около нуля (батарея не подключена), индикатор на экране не
рисуется, а в `hello` вместо заряда и напряжения уходят прочерки.

## Ветки, сборка и выпуск

`develop` — основная ветка репозитория: на неё попадает свежий клон, и в неё уезжает код
после каждой успешной сборки. Ветки `main` в проекте нет.

```bash
pio run                                 собрать, закоммитить и отправить develop
RELEASE=1 pio run                       плюс ветка release/v<версия> — она запускает выкладку
NOGIT=1 pio run                         собрать, ничего не трогая в git
python3 scripts/release.py --dry-run    посмотреть, что попадёт в коммит
```

Коммит делается только после успешной сборки: фиксировать код, который не компилируется,
смысла нет. Если изменений нет, коммит не создаётся. Сетевые ошибки сборку не роняют —
скрипт сообщит, что отправить не удалось, и оставит коммит на месте.

### Выкладка файлов прошивки

Файлы прошивки в репозиторий не кладутся (`firmware_output/` в `.gitignore`). Их собирает
и публикует GitHub Actions — `.github/workflows/build.yml`:

1. на каждый push прогоняются проверки `scripts/selftest.py` и сборка обоих окружений;
2. собранные `.bin` и `.otaz` сохраняются как артефакт запуска — их можно скачать из
   интерфейса Actions для любой ветки;
3. если ветка называется `release/v*`, создаётся релиз с тегом `v<версия>`, и файлы
   прикладываются к нему.

Шаги идут последовательно в одном задании, поэтому релиз физически не может появиться,
если упали тесты или сборка. Токен для публикации Actions выдаёт себе сам — с машины
разработчика ничего выкладывать не нужно и нечем.

Перед коммитом список файлов дополнительно проверяется на `secrets.ini`, `secrets.json`,
`firmware_output/` и `build_info.h`. Их исключает и `.gitignore`, но цена ошибки здесь —
пароли и ключи каналов в истории публичного репозитория, поэтому проверка продублирована.

## Страница OTA

Разметка страницы лежит в коде (`ota.cpp`), а стили и сценарий — обычными файлами в `web/`:
их удобно править и проверять инструментами. Перед сборкой `scripts/gen_web.py` сжимает их
в `lib/meshcore/include/web_assets.h`, и бот отдаёт готовые сжатые байты, не тратя на это
ни памяти, ни времени. В цифрах: 16.1 КБ сценария превращаются в 5.7 КБ, 4.4 КБ стилей —
в 1.4 КБ, прошивка координатора похудела на 18.5 КБ, а страница грузится вчетверо быстрее.
