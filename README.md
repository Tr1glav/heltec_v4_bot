# MeshCore-fork — координатор, сенсоры и компаньон на ESP32-S3 + SX1262

Форк прошивки MeshCore для собственной сети из плат Heltec. Одна кодовая база, три роли:

| Роль | Что делает | Окружение | Плата | Чем прошивается |
|---|---|---|---|---|
| **Координатор** | WiFi, MQTT с автообнаружением в Home Assistant, веб-страница, раздача времени, обновление сети | `heltec_v3_coordinator` | Heltec V3 | `.bin` через страницу или USB |
| **Сенсор** | только LoRa: кнопка, heartbeat, приём прошивки по воздуху | `heltec_v4_3_sensors` | Heltec V4.3 | `.otaz` по воздуху |
| **Компаньон** | то же, что сенсор, плюс BLE для телефонного приложения MeshCore | `heltec_v4_3_companion` | Heltec V4.3 | `.otaz` по воздуху |

Все узлы говорят по mesh-протоколу MeshCore и дополнительно — своими сообщениями в
«сенсорном» канале. Имя узла, ключи каналов, WiFi и MQTT в прошивку не вкомпилированы:
они лежат в NVS самого устройства. Поэтому один и тот же файл подходит всем платам своей
роли, а образ можно выкладывать открыто.

```
                    WiFi/MQTT                     LoRa 868.731 МГц
   Home Assistant <───────────> Координатор <─────────────────────> Сенсор
                                 (Heltec V3)          │
                                                      └──────────> Компаньон <··BLE··> телефон
                                                                  (Heltec V4.3)
```

## Быстрый старт

```bash
pio run -e heltec_v3_coordinator -e heltec_v4_3_sensors -e heltec_v4_3_companion   # сборка
python3 scripts/selftest.py                       # проверки на ПК, без железа
python3 scripts/provision.py flash Tr1glav_home   # прошить и настроить плату по USB
```

Готовые файлы складываются в `firmware_output/` с версией в имени, по три последних на
плату; для сенсора и компаньона сохраняется только `.otaz`.

## Признаки сборки

Роль — это не одно свойство, а набор возможностей. `lib/meshcore/include/features.h`
выводит признаки из роли, а окружение может задать любой из них явно:

| Признак | Что включает |
|---|---|
| `FEATURE_WIFI` | WiFi как таковой; от него зависят остальные сетевые признаки |
| `FEATURE_MQTT` | публикация в MQTT и автообнаружение в Home Assistant |
| `FEATURE_WEB` | страница на порту 3232 |
| `FEATURE_AUTOUPDATE` | проверка релизов GitHub и раздача прошивок узлам |
| `FEATURE_NTP` | синхронизация часов и рассылка времени в сеть |
| `FEATURE_MESH_OTA_SENDER` | раздача образа по радио |
| `FEATURE_MESH_OTA_RECEIVER` | приём образа по радио |
| `FEATURE_SENSOR` | heartbeat, кнопка, проверка связи, настройка по радио |
| `FEATURE_COMPANION` | BLE и протокол телефонного приложения |
| `FEATURE_BUTTON` | кнопка платы |

Несовместимые сочетания останавливают сборку с понятным сообщением: например `FEATURE_WEB`
без `FEATURE_WIFI` или компаньон без `FEATURE_SENSOR`. Экран включается признаком `HAS_OLED`
из `board_build` платы.

## Настройка устройства

Настройки живут в разделе `nvs`, отдельном от разделов прошивки, поэтому переживают любое
обновление — и по USB, и по воздуху. Стирает их только полное стирание флеша
(`esptool erase_flash`). Ненастроенное устройство не выходит в эфир; на экране — `NO CONFIG`.

### Скриптом

Значения лежат в локальном `secrets.json` (он в `.gitignore`, шаблон —
`secrets.example.json`), `scripts/provision.py` прошивает плату по USB и записывает
настройки в её NVS через консоль. Секреты в вывод не попадают: вместо значений печатается
длина.

```bash
python3 scripts/provision.py list                  # какие платы видны
python3 scripts/provision.py show <имя>            # что будет записано
python3 scripts/provision.py flash <имя>           # собрать, прошить, настроить, сверить
python3 scripts/provision.py config <имя>          # только настроить
python3 scripts/provision.py verify <имя>          # сверить настройки с файлом
```

Устройство выбирается по **имени узла** — это ключ в разделе `devices`. Раздел `common`
задаёт общие значения, поля устройства их перекрывают. Набор полей зависит от роли:

| Роль | Поля |
|---|---|
| `bot` (координатор) | имя, WiFi, MQTT, приватный и сенсорный каналы, канал команд, радио |
| `sensor` | имя, сенсорный канал, радио |
| `companion` | имя, приватный и сенсорный каналы, радио |

Компаньону приватный канал нужен потому, что в приложении это обычный чат: без ключа он в
списке каналов не появится.

Записываются только поля, отличающиеся от текущих настроек платы. Ключ `--force` пишет всё.
Консоль у V3 — на мосте CP2102 (`/dev/ttyUSB*`), у V4.3 — нативный USB (`/dev/ttyACM*`).

### Консолью

USB на 115200 (`pio device monitor`):

```
help                      список команд
show / show all           настройки (во втором виде — с паролями)
set name Tr1glav_sensor   имя узла: адресат прошивки по радио и устройство в Home Assistant
set sns_name / sns_key    канал сенсоров (нужен всем ролям)
set prv_name / prv_key    приватный канал (координатор и компаньон)
set wifi_ssid / wifi_pass только координатор
set mqtt_host …           только координатор: ещё mqtt_port, mqtt_user, mqtt_pass
set tx_ch #connections    канал для команд из Home Assistant
set lora_freq 868.731018  радио: ещё lora_bw, lora_sf, lora_cr, lora_tx, lora_pre, lora_sync
set tz 3                  часовой пояс, часы от UTC
set disp_bri 255          яркость экрана 0..255
set vext_on 0             уровень, включающий питание периферии
set auto_upd 1            ставить новые версии из релизов GitHub
bri <0..255> / vext <0|1> применить сразу, без сохранения
save / reboot             записать в NVS / перезагрузить
```

Параметры радио обязаны совпадать у всех узлов сети. Имя узла обязано быть уникальным.

### Версия

`version.txt` хранит версию, хэш исходников и время сборки. `scripts/gen_version.py` перед
сборкой считает хэш `src/`, `lib/`, `boards/`, `variants/` и `platformio.ini`: изменился
код — номер сборки растёт. Значения попадают в код через сгенерированный `build_info.h`.
Сборка с `RELEASE=1` получает чистый номер, остальные — с суффиксом `dev`, чтобы на экране
было видно, что прошивка не из релиза.

## Компаньон: телефонное приложение по BLE

Компаньон — сенсорный узел, к которому по Bluetooth подключается официальное приложение
MeshCore. Протокол повторён по оригиналу: сервис Nordic UART (`6E400001-…`), кадр
`[код][данные]`, числа little-endian, до 176 байт в кадре.

**Сопряжение.** Обе характеристики доступны только по зашифрованной связи с подтверждением
личности (`ESP_GATT_PERM_*_ENC_MITM`, режим `SC_MITM_BOND`). Код сопряжения —
шестизначный, случайный при каждом запуске — показывается во весь экран и держится там,
пока сопряжение не состоится. Размер пакета задаётся явно (`setMTU(176)`), иначе длинные
ответы не помещаются в уведомление. Когда телефон подключён, в правом верхнем углу экрана
горит значок Bluetooth.

**Команды**

| Команда | Что делает |
|---|---|
| 1 `APP_START`, 22 `DEVICE_QUERY` | представиться: ключ, радио, версия, вместимость; здесь же приложение сообщает версию протокола |
| 5 / 6 `GET/SET_DEVICE_TIME` | часы устройства |
| 4 `GET_CONTACTS`, 9 `ADD_UPDATE_CONTACT`, 15 `REMOVE_CONTACT`, 30 `GET_CONTACT_BY_KEY` | список узлов |
| 13 `RESET_PATH`, 42 `GET_ADVERT_PATH` | маршрут до узла: забыть и показать |
| 31 `GET_CHANNEL`, 32 `SET_CHANNEL` | каналы: перечисление и вступление |
| 2 `SEND_TXT_MSG`, 3 `SEND_CHANNEL_TXT_MSG` | личное сообщение и сообщение в канал |
| 10 `SYNC_NEXT_MESSAGE` | забрать входящее из очереди |
| 7 `SEND_SELF_ADVERT`, 8 `SET_ADVERT_NAME` | объявить себя, переименоваться |
| 20 `GET_BATT_AND_STORAGE` | заряд |
| 54, 64 | области рассылки: у нас их нет, отвечаем «не задана» |

Остальные команды получают отказ `ERR_CODE_UNSUPPORTED_CMD`.

**Контакты** строятся из адвертов: ключ, имя, тип, координаты и маршрут, которым пришёл
адверт. Список хранится файлом в LittleFS (до 200 узлов) и переживает перезагрузку. Новый
узел уходит в приложение полным кадром, знакомый — коротким.

**Ограничения.** Подтверждений доставки прошивка не отслеживает, поэтому метка в ответе на
личное сообщение нулевая. Текст личного сообщения — до 200 байт, входящее сообщение канала
— до 165 байт: столько несёт кадр BLE. Каналы, заданные настройками устройства, приложению
на запись не отдаются. Сообщения, отправленные самим устройством, попадают в переписку без
сигнала «есть новое», чтобы телефон не показывал уведомление о собственном действии.

## Сообщения в сенсорном канале

| Сообщение | Кто шлёт | Смысл |
|---|---|---|
| `hello:<версия>:<заряд %>:<напряжение>:<код платы>:<окружение>` | узел | heartbeat раз в 10 минут, при старте и по запросу; `-` вместо значения, если заряд не измеряется |
| `hello?` | координатор | просьба отметиться; узлы отвечают со случайной задержкой до 4 с |
| `button` / `button2` | узел | одиночное и двойное нажатие |
| `ping:<номер>` | узел | проверка связи по тройному нажатию |
| `pong:<номер>:<rssi>:<snr>` | координатор | ответ с его уровнем приёма |
| `time:<epoch>:<версия>` | координатор | синхронизация часов раз в 5 минут |
| `ota:…` | обе стороны | управление прошивкой по радио |
| `cfg:<имя>:<поле>=<значение>` | координатор | настройка узла по радио; также `:save`, `:reboot`, `:get` |
| `cfg:ok:…` / `cfg:err:…` / `cfg:val:…` | узел | подтверждение, отказ, текущие несекретные настройки |

Поле окружения в `hello` определяет, какой файл релиза получит узел: сенсор и компаньон
стоят на одной плате с кодом `h43`, и без него обновление залило бы компаньону образ
сенсора. Узлы со старой прошивкой окружения не передают — для них файл подбирается по коду
платы.

Всё, что приходит от узлов, координатор публикует в MQTT: `<префикс>/sensor/<имя>/` +
`text`, `rssi`, `version`, `battery`, `voltage`, `board`, `available`, `button`. В поле
`board` уходит имя окружения, а карточка устройства в Home Assistant называется по роли —
`MeshBot Companion <имя>` или `MeshBot Sensor <имя>`.

## Кнопка и проверка связи

Длительность нажатия определяет действие:

* короче секунды — идёт в счёт серии: одно нажатие `button`, два `button2`, три запускают
  проверку связи с координатором;
* дольше двух секунд — переключает экран: горит гаснет, погасший зажигается;
* промежуток от секунды до двух не делает ничего — так отсекается случайное удержание.

Окно между нажатиями серии — 700 мс (`SNS_BTN_DBL_WINDOW_MS`). Счёт ведётся без остановки
главного цикла, поэтому приём радио и BLE не задерживаются.

Результат проверки связи держится на экране 15 секунд:

```
LINK TEST
rtt:  412 ms
rx:   -52 dBm
snr:  9.0 dB
peer: -48 dBm
hops: 0 (direct)
```

Запрос уходит одиночной посылкой, а не повторами: иначе во время ответа мерялись бы
повторы. Строка `peer` — уровень приёма у координатора, поэтому асимметрия канала видна
сразу. Если ответа нет за 5 секунд, так и пишется. Экран устройства везде на английском.

## Эфир

Сообщение уходит **дважды** с паузой 60 мс (`FLOOD_RETRY_MS`): приёмник отбрасывает
дубликат по хэшу, а вторая копия спасает от коллизии.

Старшие два бита байта длины пути задают размер хэша ретранслятора, младшие шесть — число
хопов. Вся сеть считает одинаково: **два байта на хоп** (`PATH_HASH_SIZE`), то есть меньше
совпадений хэшей, а при пути в 64 байта — до 32 ретрансляций.

Ответ на `/ping` и на личное сообщение уходит через 900 мс (`PING_REPLY_DELAY_MS`): пока
отправитель шлёт свои повторы, он при полудуплексном радио ничего не слышит.

Мощность передатчика задаётся настройкой `lora_tx`; по умолчанию 20 дБм на V3 и 22 дБм на
V4.3 (предел SX1262).

## Энергосбережение

Узлы работают от аккумулятора, поэтому:

* экран гаснет после двух минут простоя (`SCREEN_IDLE_OFF_MS`) и зажигается длинным
  нажатием кнопки; пока компаньон не сопряжён с телефоном, экран не гаснет — на нём код;
  во время прошивки по радио экран зажигается принудительно и не гаснет до конца сессии;
* процессор работает на 80 МГц (`CPU_MHZ_IDLE`) и поднимается до 240 МГц на время прошивки
  по радио, где кадры идут каждые 8 мс;
* BLE объявляет себя раз в 800–1200 мс, пока никто не подключён.

Координатор питается от сети, и к нему это не применяется.

## Автообновление из релизов GitHub

Координатор раз в 6 часов спрашивает у GitHub последний релиз и сверяет версии; ту же
проверку запускает кнопка «Проверить обновления» на странице, и она не смотрит ни на
расписание, ни на настройку `auto_upd` — нажатие и есть согласие.

Файл выбирается по имени окружения узла: `<окружение>_v<версия>.otaz` для узлов и
`<окружение>_v<версия>.bin` для самого координатора. Сначала обновляются узлы — по одному
за проход, потому что прошивка по радио занимает эфир целиком, — и лишь потом координатор
сам себя. После начатой сессии следующая проверка идёт через 10 минут.

Сеть работает в отдельной задаче, поэтому во время скачивания страница отвечает, а радио
обслуживается.

Адрес ассета релиза представляет собой перенаправление на стороннее хранилище. Конечную
ссылку координатор узнаёт отдельным запросом `HEAD` к GitHub, а сам образ тянет уже с этой
ссылки отдельным соединением. Загрузка повторяется до трёх раз с паузой, пока связь не
сорвётся окончательно.

Образ пишется в LittleFS кусками, и каждый кусок сразу сбрасывается на флеш. По окончании
скачивания размер файла сверяется с количеством принятых байт: файл, в котором не хватает
конца потока, в работу не принимается и качается заново. Прежний образ остаётся на месте,
пока новый не скачан целиком, — оборванная загрузка не отнимает у сети рабочую прошивку.

Ход скачивания виден на странице в виде полосы: проценты, принятые байты, для кого образ и
номер попытки, если первая не удалась. Пока образ качается, кнопка «Начать обновление»
недоступна.

Прошивка не содержит секретов, файлы релиза лежат открыто и качаются без токена.
Сертификаты не проверяются: защита здесь другая — маркер платы в образе и CRC32, которые
проверяются до записи.

## Прошивка узла по радио

1. Координатор получает `.otaz` и сохраняет в LittleFS.
2. `ota:start:<имя>:<размер образа>:<crc32>:z<размер сжатого потока>` — в сенсорном канале.
3. Узел отвечает `ota:ackstart:1`, обе стороны переходят на быстрый канал (GFSK
   250 кбит/с, девиация 125 кГц, полоса приёмника 467 кГц, 868.95 МГц) и общаются сырыми
   кадрами вне meshcore. Полоса покрывает `2*(девиация + скорость/2)`, а индекс модуляции
   `2*девиация/скорость` держится около единицы.
4. Координатор шлёт пачками по 16 кадров: `[BE EF][тип][seq 4B][MAC 2B][шифр][crc16 2B]`,
   чанк 240 Б, шифрование ключом канала. Последний кадр пачки просит подтверждение.
5. Узел отвечает `WACK`: номер первого недостающего чанка и битовая маска следующих.
   Потерянные кадры уходят заново, целую пачку переспрашивает кадр `POLL`.
6. `DONE` → узел сверяет CRC32 всего образа, пишет его и перезагружается, ответив
   `DONE_ACK`. При отказе он присылает причину текстом, и она попадает в журнал
   координатора.

Узел распаковывает поток на лету (`tinfl` из ROM ESP32-S3), поэтому по радио идёт сжатый
образ — около 60% исходного размера. Образ сенсора на 270 КБ уходит примерно за 38 секунд.

**Формат `.otaz`:** `[OTAZ][размер образа 4B LE][CRC32 образа 4B LE][zlib-поток]`, собирает
`scripts/copy_firmware.py`.

**Маркер платы.** Каждая прошивка несёт строку `MBFW:<код платы>:<версия>`. Принимающая
сторона ищет её в образе и отклоняет прошивку от другой платы до записи.

## Веб-страница координатора (порт 3232)

| Адрес | Назначение |
|---|---|
| `/` | страница: цели, загрузка файла, прогресс, живые логи |
| `/style.css`, `/app.js` | статика из `web/`, отдаётся сжатой |
| `/info` | состояние: uptime, WiFi/MQTT, IP, температура, память, заряд, окружение, файл |
| `/sensors` | список узлов: версия, окружение, заряд, RSSI, когда выходил на связь |
| `/sensors/hello` | разослать `hello?` |
| `/update` | самопрошивка координатора `.bin` |
| `/savefw` | загрузка `.otaz` |
| `/ota/start`, `/ota/abort`, `/ota/status` | управление сессией и её состояние |
| `/fw/check` | проверить обновления и поставить их |
| `/fw/status` | ход скачивания образа для узлов: JSON с фазой, принятым/общим объёмом, попыткой и адресатом |

| `/config` | настройки координатора: `GET` — список полей, `POST` — изменить |
| `/sensors/config` | настройки узла по радио: `target`, поля, `save`, `reboot`, `get` |
| `/selftest` | проверка записи в LittleFS |

Страница открыта без пароля: любой в сети может прошить координатор или узел.

Разметка лежит в коде, стили и сценарий — файлами в `web/`. Перед сборкой
`scripts/gen_web.py` сжимает их в `web_assets.h`, и координатор отдаёт готовые сжатые
байты.

## Настройка узлов по радио

Со страницы можно менять настройки узла, не подключая его по USB: поля уходят по одному в
сенсорный канал, узел подтверждает каждое сообщением `cfg:ok:<поле>`, ответы видны в
журнале. Команды уходят с паузой в две секунды: радио полудуплексное, а подтверждение узла
занимает эфир около секунды.

Присваивание идёт только в память узла. В NVS настройки попадают по команде `save`. Если
правки были, а `save` не пришёл за две минуты (`CFG_PENDING_REVERT_MS`), узел
перезагружается и возвращается к сохранённым настройкам.

Смена имени, ключа или имени канала и параметров радио после сохранения уводит узел из
сети — вернуть его можно будет только по USB. Страница предупреждает об этом.

## Питание периферии и экран

Питание периферии (`Vext`) на обеих платах включается низким уровнем; значение задаётся
настройкой `vext_on`. Яркость (`disp_bri`, 0..255) применяется в конце инициализации:
раскладка на регистры контраста, предзаряда и VCOMH завершается командами включения
экрана. Если напряжение батареи около нуля, индикатор заряда не рисуется, а в `hello`
вместо заряда и напряжения уходят прочерки.

## Ветки, сборка и выпуск

`develop` — основная ветка: на неё уезжает код после каждой успешной сборки.

```bash
pio run                                 собрать, закоммитить и отправить develop
RELEASE=1 pio run                       плюс ветка release/v<версия> — запускает выкладку
NOGIT=1 pio run                         собрать, ничего не трогая в git
python3 scripts/release.py -m "текст"   зафиксировать со своим описанием
```

Коммит делается только после успешной сборки. Описание по умолчанию перечисляет области
правки (например `v0.2.4: сборка, OTA, скрипты`), но для значимых изменений лучше задавать
его явно: из этих сообщений собирается описание релиза.

Файлы прошивки публикует GitHub Actions (`.github/workflows/build.yml`): на каждый push
идут проверки `scripts/selftest.py` и сборка всех трёх окружений, собранное сохраняется
артефактом, а для ветки `release/v*` создаётся релиз с тегом `v<версия>`. Описание релиза
собирается из коммитов с предыдущего тега плюс сводка изменённых файлов.

Перед коммитом список файлов проверяется на `secrets.ini`, `secrets.json`,
`firmware_output/` и `build_info.h`.
